How the read & write pointers share one tape

A single GPU ring buffer, one write position per channel. The record head advances it; the read head trails it by one slot. Draw order is the whole trick — and it's what makes the realized delay land at loop_length + 1.

source→ Delay Tap · read→ fx…→ Delay Write · record→ output

03 What each head computes

Two independent gains at the read, a gated crossfade at the write
Delay Tap — read (TAP-READ-MATH)
out = clamp( Dry·source + Wet·tape[wp+1] , 0, 1 )
Dry and Wet are independent gains, not a crossfade — full new material and full tail can run at once. Wet is force-muted while the tape is empty.
Delay Write — record (WRITE-RECORD-MATH)
tape[slot] = (1−Send)·Regen·old + Send·input
A fade pre-pass scales the slot by (1−Send)·Regen, then an additive CONSTANT_COLOR = Send write lays the input in. Regen is gated by (1−Send) so the two feedback paths can't double-count.
Per-lap loop feedback (LOOP-FEEDBACK-COEFF) — Tap + Write on the same channel
feedback = (1−Send)·Regen + Send·Wet    ·    injection = Send·Dry·source
≥ 1 sustains or blooms, < 1 fades. At Send = 1 the tail is governed by Wet alone (Regen drops out).
⚠ Known off-by-one · CORE-DEPTH (open for the user to rule on)

The read slot (wp+1) mod buf_size is identically the slot this frame's Write advances into. What keeps the read clean is draw order (Tap before Write), not a spare slot. The lone effect of buf_size = loop_length + 1 is that realized delay is loop_length + 1, not loop_length. Fix is a one-line choice: set buf_size = loop_length so the delay matches the knob, or state in the UI that delay is loop_length + 1. The spec currently describes the as-built +1 behaviour.
