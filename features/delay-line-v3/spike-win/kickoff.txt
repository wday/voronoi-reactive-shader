● Committed (100af1c). Here's the summary of where delay-line v2 stands.

  Delay-Line v2 — Read/Write model

  The core idea: split the delay into two plugin instances — Read and Write —
  with a Resolume FX chain between them. That FX-insert point is the whole
  reason v2 exists: it lets Resolume effects process the feedback signal before
  it's written back to the buffer, which the old Send/Receive model couldn't do.

  Signal flow:
  Source → [gain/exposure] → Read → [FX insert] → Write → Output
                              │                      │
                      Resolume blends                ↓
                      input + buffer read        Ring Buffer
                              ↑                      │
                              └──────────────────────┘

  Division of labor — this is the key simplification:
  - Read is trivial: outputs buffer[read_pos], nothing else. No timing, no
  mixing, no feedback param. All mixing is delegated to Resolume's native
  controls — effect opacity + blend mode on Read = feedback level; a
  gain/exposure effect before Read = send level.
  - Write owns everything stateful: timing, buffer management, write_pos
  advance, and decay. It outputs what it wrote.

  The N+1 stitch (the subtle bit): naively reading buffer[write_pos] gives a
  1-frame delay regardless of loop length, because Read sees what Write wrote
  last frame. Fix: allocate loop_length + 1 slots and have Read read (write_pos 
  + 1) % buf_size — the oldest slot, which is exactly loop_length frames old.
  The +1 prevents read/write aliasing the same frame. Registry returns buf_size
  so Read computes its own position without knowing timing.

  How overdub folds in: the IFS-accumulation goal (beat-synced fractal
  attractors) doesn't need its own model. decay on Write scales prior buffer
  content before the new write; additive accumulation across contractive maps
  happens via Resolume blend modes on Read — not plugin-side GL_BLEND(ONE,ONE)
  multi-Send coordination. features/overdub/ survives as the validation
  composition that proves v2 out.

  Status: requirements + plan + devlog are complete and now committed. No code 
  yet. Implementation order per the plan:
  1. Registry (registry.rs) — N+1 buffer sizing, read_channel returns buf_size
  2. Params (params.rs) — restructure (drop Passthrough; 8→7 params)
  3. Read/Write passes (shader.rs, delay.rs) — trivial Read pass, Write owns
  timing + decay

● That registry read confirms the crux. Here's the key architectural fact before
  we design:

  The two modes share the ring buffer through a process-global Rust static 
  REGISTRY (registry.rs:23). That works only because Read and Write are the same
  DLL. FFGL is one-plugin-per-DLL, so splitting into two plugins means two DLLs
  — and each DLL gets its own copy of that static. Read in one DLL would not
  see Write's buffers in the other. So the split is the right ergonomic call,
  but it's not free: it needs the buffer registry shared across DLLs. Two ways
  to do that (decide in the plan):
  - A small shared "delay-core" dynamic lib both plugins call into — keeps
  today's Mutex<[ChannelBuffer;2]> registry verbatim, just relocated so there's
  one copy. Cost: ship one more lib + set its load path (@loader_path / DLL
  dir).
  - OS shared memory (named segment) holding the tiny registry table. GL texture
  handles are process-global in Resolume's shared GL context, so passing the
  GLuint across works. Cost: a process-shared lock + stale-segment cleanup.

  Either is bounded work, but it's real. Worth knowing this is why it was built
  unified in the first place.

  On wet/dry — I think your instinct is right, and there's a clean unifying idea

  You're circling the correct design. Right now Read ignores its own input 
  texture entirely and leans on Resolume's effect opacity to blend — and your
  doubt is well-founded: I can't confirm Resolume actually crossfades an FFGL
  effect's output against its input via the opacity slider. Either way the fix
  is the same: stop relying on host opacity, add a real in-plugin Dry/Wet.

  The unifying mechanic: output = mix(this node's input, the delayed frame from 
  the buffer, wet). Then:
  - On Write it's exactly what you described — "block the thru and play back the

  trickery.

  defaults wet). That answers your "maybe we need both" — yes, and they're the

❯ Is there enough compute overhead to take on the float buffers, but spatially  
  compress/expand to tradeoff bit depth for compute resourrce                   

● Short answer: yes — and the numbers actually favor it. Trading spatial
  resolution for bit depth is a real, well-known move and here it's close to
  free, because the two costs multiply into the same VRAM/bandwidth budget.

  The math (240 frames, per channel):

  ┌───────────────┬─────────┬──────────┬─────────┐
  │    Format     │   Res   │ Bytes/px │ VRAM/ch │
  ├───────────────┼─────────┼──────────┼─────────┤
  │ RGBA8 (today) │ 1080p   │ 4        │ ~1.9 GB │
  ├───────────────┼─────────┼──────────┼─────────┤
  │ RGBA16F       │ 1080p   │ 8        │ ~3.8 GB │
  ├───────────────┼─────────┼──────────┼─────────┤
  │ RGBA16F       │ 720p    │ 8        │ ~1.8 GB │
  ├───────────────┼─────────┼──────────┼─────────┤
  │ RGBA16F       │ 960×540 │ 8        │ ~1.0 GB │
  └───────────────┴─────────┴──────────┴─────────┘

  So 720p-float ≈ 1080p-8bit on memory, and half-res float is cheaper than what
  you run today. And compute goes the right way: fragment-shader work scales
  with pixel count, so lower-res float does fewer invocations than full-res
  8-bit. The compress/expand itself is near-free — write renders into the
  smaller layer (fewer fragments), read upsamples in the sampler (LINEAR
  filtering, one texture fetch). You're not spending more; you're reallocating
  the same budget from "spatial samples" to "levels per sample."

  Two things that make this more than a wash:

  1. Float is the only format that can store over-unity. RGBA8 and RGB10_A2 are
  UNORM — they clamp at 1.0. RGBA16F holds values >1.0 in the buffer. That's not
  just anti-banding; it's the actual enabler for the reviewer's "controlled
  runaway / boil-over past unity" — bright regions can accumulate and bloom
  internally across generations, then tone-map/clamp only at display. Float and 
  past-unity Regen are the same decision. You can't do genuine over-unity
  feedback in an 8-bit buffer.
  2. There's a free middle option: RGB10_A2 — 4 bytes/px (same VRAM as today),
  but 1024 levels/channel instead of 256. That kills most visible 8-bit banding
  at zero cost, if you don't need the over-unity headroom. Good default; float
  is the upgrade when you want runaway.

  The one trap to name: in a Tap→FX→Write loop, if the buffer is lower-res than
  the FX/output, every generation does downsample→upsample — which is itself a
  lowpass. So float-low-res buys you deep smooth tones that survive hundreds of 
  generations (no banding, faint accumulating copies preserved) but soft fine 
  detail (high-frequency filigree blurs each pass). That's a coherent aesthetic,
  not a bug — but it's "deep, not crisp." Interestingly it suits IFS:
  contractive maps shrink structure sub-pixel each iteration anyway, so
  precision to hold faint layered copies matters more than raw resolution.
  Nearest vs linear filtering then becomes the crisp-vs-soft dial on top.

  What this does to the decision: it dissolves the reason you skipped "float
  precision + more channels" — those were bundled, but they're independent.
  Float via the res-tradeoff is cheap and unlocks over-unity; the channel-count
  increase is the genuinely VRAM-expensive part. So I'd split them: fold float 
  precision (as a resolution/precision budget knob) into v1, keep channel count
  as the fast-follow.

  Concretely that suggests one describable macro — Buffer: Crisp ↔ Deep — that
  slides precision up while auto-scaling buffer resolution to hold VRAM
  constant, with precision (8 / 10-bit / 16F), res-scale, and filter exposed
  underneath for the advanced path.

  Want me to fold float-via-tradeoff into v1 on those terms, and leave
  channel-count as fast-follow?
